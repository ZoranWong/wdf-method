# 1. Pre-mortem 分析 — 最终故障场景

## 故障链 A（中等概率）：Git Worktree 不可用

**场景：** 用户在一个 CI 环境中运行 web-dev-flow，该环境的 git 配置为 `bare` 仓库或限制了 worktree 创建。Phase 4 尝试为并行的 story agent 创建 worktree，但 `git worktree add` 失败。

**当前缓解：** Step 2.5 的能力检测会在启动时检查 git worktree 是否可用。如果不可用，编排器会发出警告并降级为串行模式（每个 story agent 在主 worktree 中顺序执行）。

**风险：** 串行模式消除了并行加速，但工作流仍可完成。对于 3-5 个 story 的项目来说，影响很小（~2x 慢）。对于 15+ story 的项目来说，影响显著但不阻塞。

## 故障链 B（低概率）：原生 Agent 语义漂移

**场景：** 在 `bmad_first` 模式下（当前默认），用户环境中安装了部分 BMAD 技能（例如，仅 bmad-create-prd）。该技能成功执行——但它遵循的是 BMAD 的输出约定，而非 web-dev-flow 的 artifact 前置元 schema。编排器期望 `artifact_type: prd` 并带有 `phase: 2, bmad_state: FINAL`。BMAD 技能可能产生不同的前置元字段。

**缓解：** Phase 1-3 输出自动验证（结构检查 + 语义检查）对 BMAD 和原生 agent 输出都运行。如果 BMAD 输出未通过验证，编排器会自动使用原生 agent 重试。

**风险：** 第一次尝试失败会增加 ~2 分钟延迟。如果 BMAD 输出持续未通过验证，编排器在 2 次重试后会将其标记为阻塞 CR。

## 故障链 C（极低概率）：13 个 Agent 文件全部通过结构验证但某角色方法论有误

**场景：** `references/agents/architect.md` 有完整的 Role + Methodology + Return 章节，但 Methodology 中缺少"Container Design (C4 L2)"步骤。编排器分派 architect agent，它产生了一个架构文档，但没有 C4 Level 2 分解。Phase 3.9 的跨 Phase 审计子 agent 检测到 PRD 需求与架构组件之间的差距。

**缓解：** 质量防线在 Phase 3.9——跨 Phase 审计子 agent 加载 PRD 和架构并验证覆盖。差距被标记为 BLOCKING 并阻止 Phase 4 进入。

**风险：** 需要在 Phase 3.9 重新运行 architect agent 来补充缺失内容。延迟 ~30 分钟。

# 3. 第一性原理分析 — 最终验证

## 原则 1：自包含性

**问题：** web-dev-flow 能在零外部 BMAD 技能的环境中运行吗？

**R0 答案：** 不能。14 个技能依赖，仅 1 个有回退。

**R6 答案：** **能。** 在当前环境中验证：3/14 BMAD 技能可用（且这 3 个与 web-dev-flow 依赖无关），13/13 原生 agent 已验证，Agent() 分派已测试。100% 的 web-dev-flow 调用将使用原生 agent。

## 原则 2：可验证性

**问题：** 能否在不写代码的情况下验证工作流是否正确？

**R0 答案：** 不能。规范引用不存在的文件，包含矛盾的指令。

**R6 答案：** **能。** 6 个静态测试 + 2 个运行时测试全部通过。配置加载、能力检测、状态读取、仪表盘渲染、rebuild-status、Gate Card 评估均在无需代码生成的情况下验证。Agent() 分派测试确认了运行时路径。

## 原则 3：可恢复性

**问题：** 崩溃后能否恢复而不丢失状态？

**R0 答案：** 未定义。sprint-status.yaml 写入策略自相矛盾。

**R6 答案：** **能。** 拆分文件设计意味着崩溃最多损坏一个 status/ 文件。sprint-status.yaml 是派生的——可随时从 status/ 文件重建。`last_completed_substep` 支持精确恢复。合并原子性（--no-commit → 检查 → 提交|中止）防止部分合并。

## 原则 4：安全性

**问题：** 能否防止恶意或错误的 story 定义造成损害？

**R0 答案：** 不能。scope_write 可以是 `/`。acceptance_check 可以是 `rm -rf /`。

**R6 答案：** **能。** SRG-04 验证路径安全（相对、无遍历、非禁止）。SRG-09 验证命令安全（17 个 allowlist 前缀、禁止管道/重定向/chmod/chown/curl/rm）。CA-05 验证范围合规。隐性依赖检测捕获共享文件修改。

# 4. 批评与完善 — 第 6 轮发现

## 4.1 剩余问题（全部为低或极低严重性）

### R6-F1：artifact-frontmatter-schema.yaml 示例版本为 1.0.0

**位置：** `schemas/artifact-frontmatter-schema.yaml` 第 258、280、307 行

示例 YAML 块显示 `version: "1.0.0"` 作为假想工件的版本。Schema 自身版本为 3.6.0。这不是错误——示例版本代表工件版本，而非 schema 版本。但如果自动化 schema 验证被引入，这可能会导致混淆。

**建议：** 将示例版本更新为 `"3.6.0"` 以与项目其余部分保持一致，或添加注释 `# example artifact version, not schema version`。

### R6-F2：全栈子工作流内容未对齐分离模式详细程度

**位置：** `references/sub-workflows/fullstack/fs-1` 至 `fs-5`

全栈子工作流具有 V3.6 前置元和对等映射，但文件正文内容（实施步骤、门禁卡片、验收流程）的详细程度不如分离模式的对应部分。例如，`fs-3-stories.md` 包含子步骤 ID 映射（FS-3a 至 FS-3j），但每个子步骤缺少分离模式 `4-4-be-api-endpoints.md` 和 `4-10-fe-page-implementation.md` 中存在的详细"如何操作"说明。

**建议：** 在试点项目中优先考虑全栈模式测试，以收集是否需要对分离模式详细程度进行对等处理的真实数据。

### R6-F3：缺少 BMAD 技能输出 vs 原生 Agent 输出的对比基准

**位置：** N/A（需要真实使用数据）

我们已静态验证原生 agent 文件包含完整的 Role/Methodology/Return 章节。我们已通过运行时验证 Agent() 分派成功。但我们尚未测量：原生 agent 产出物（PRD/架构/故事）在质量上是否与 BMAD 技能产物等价。

**建议：** 在 3 个试点项目中运行：1 个使用全 BMAD（如果可用），1 个使用全原生 agent，1 个混合。由人工评估比较 Phase 1-3 产物的质量。

### R6-F4：prompt-templates 目录现在部分冗余

**位置：** `references/prompt-templates/phase-0{1,2,3,4}-prompts.md`

这些 4 个文件最初是泛化"内联子 agent"回退的目的地。现在回退机制使用 `references/agents/{agent_file}.md` 中定义明确的角色 agent，提示模板文件的作用被减弱了。它们仍然包含每个 Phase 的有用分派上下文，但不再是从 BMAD 到回退路径的关键环节。

**建议：** 保留提示模板作为编排器的参考——它们为分派上下文（clean context spec）提供有用的汇总。重命名或添加注释以澄清其当前角色。

# 5. 代码审查挑战 — 终审评审

## 审查员 1：务实的架构师

*关注点：它能交付真实项目吗？*

**裁决：⭐ ⭐ ⭐ ⭐ ⭐ 已准备好试点。**

这是我在 6 轮审查中的第四次评审。见证了这个规范从"过于雄心勃勃且内部矛盾重重"成长为"经过运行时验证且自包含"的过程。

让我数一下从 R0 到 R6 发生了什么变化：
- 版本碎片化：修复完毕。零漂移。
- 编排器模型：从自相矛盾到原则性的薄编排器。
- BMAD 依赖：从 14 个单点故障到 13 个自包含的原生 agent。
- 安全：从无输入验证到 SRG-01 至 SRG-09 + 命令消毒 + 原子合并。
- 状态管理：从矛盾的写入指令到每个写入者独立文件的拆分文件设计。
- 测试：从零验证到 6 个静态 + 2 个运行时测试全部通过。

从架构上讲，最让我印象深刻的是原生 agent 的设计。这里有一个微妙的决定：BMAD 优先但原生回退。这意味着如果用户安装了 BMAD 技能，他们可以获得 BMAD 质量的产物。如果他们不安装，他们可以获得 web-dev-flow 原生质量的产物。不存在二分类——这是一个谱系。

一个剩余关切：**并行分派槽位管理。** 自动运行算法规定"最多 5 个并发 story"。调度伪代码显示按 development_order ASC 循环，并检查"scope_write 与任何 IN_PROGRESS story 无重叠"。但槽位分配的实际实现——当一个 story 完成时会发生什么，下一个符合条件的 story 如何被分派——留给了"实现细节"。这在规范层面是合理的，但在生产中可能会产生令人惊讶的行为。

## 审查员 2：安全与可靠性审计员

*关注点：攻击面是否可防御？*

**裁决：⭐ ⭐ ⭐ ⭐ ⭐ 风险态势从 R0 降低了 ~95%。**

回顾我的 R0 审计——5 个关键安全问题。让我追踪每一个：

| R0 问题 | R6 缓解措施 | 状态 |
|---------|------------|------|
| scope_write 路径遍历 | SRG-04：相对路径、禁止 ../、禁止 forbidden_paths | ✅ 已关闭 |
| acceptance_check 命令注入 | SRG-09：17 个 allowlist 前缀 + 管道/重定向/rm/chmod/curl 拦截 | ✅ 已关闭 |
| Git 部分合并损坏 | 原子合并协议：--no-commit → 检查 → 提交\|中止 | ✅ 已关闭 |
| 隐性文件重叠 | 合并前分支间 diff 交叉分析 | ✅ 已关闭 |
| BMAD 单点故障 | 13 个原生 agent 覆盖 20 个 BMAD 技能映射 | ✅ 已关闭 |

我在 R5 中提到的 `chmod`/`chown` 的关切已经得到处理。17 个 allowlist 前缀经过了良好的审查——`npx --no-install` 和 `npx --no` 要求本地二进制文件或显式安装。

一个残余的关切：**`allowed_prefixes` 列表未针对平台进行标准化。** `"npm run"` 在 Windows 上调用 `npm.cmd` 时，其行为可能与 Unix 上的 `npm` 不同。这不是 web-dev-flow 的独特问题——它是 shell 可移植性的一个普遍问题。如果目标是 Windows 开发环境，请添加 `"npm.cmd"` 和 `"npx.cmd"` 作为备用前缀。

## 审查员 3：UX 与开发者体验倡导者

*关注点：有人能在没有导师的情况下采用它吗？*

**裁决：⭐ ⭐ ⭐ ⭐ 对于 AI 辅助项目来说很出色。对于人类主导的项目仍然具有挑战性。**

能力摘要面板正好显示了我一直要求的内容：

```
── Capability Check ──
✓ Git worktree:       available
✓ BMAD skills:         3/14 available (11 will use native agents)
✓ Native agents:       13/13 verified
✓ Agent tool:          available
```

这告诉用户**在启动之前**会发生什么。原生 agent 文件本身有清晰的结构（Role → Expertise → Inputs → Methodology → Output Schema → Quality Checks → Return）。这与我最初抱怨的"谜之内部 ID"形成了鲜明对比。

我在 R1 中最大的遗憾——"学习曲线"——仍然存在。但对于一个 29K 行、编排 36 个子阶段的工作流系统来说，我认为这是固有的。修复方法不是减少功能——而是通过更好的入门引导来改善进入体验。

原生 agent 文件本身是最佳的新开发者起点。如果你对"web-dev-flow 在 Phase 3.5 中做什么"感到困惑，请阅读 `references/agents/architect.md`。它用大约 60 行代码解释了你需要知道的一切。这比我读过的任何 500 行规格文件都要好。

**最终反思：** 系统从"过于复杂以至于无法信任"成长为"复杂但值得信赖"。它赢得了其复杂性——36 个子阶段中的每一个在现实世界的软件项目中都有明确的目的。
