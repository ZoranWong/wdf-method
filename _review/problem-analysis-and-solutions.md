## 二、仍存在的问题

### 2.1 运行时未知——需要真实 AI Agent 执行环境验证

| 问题 | 风险 | 表现 |
|------|------|------|
| Agent 工具分派是否可用 | 高 | 整个 Phase 4 依赖 `Agent({ isolation: "worktree" })` 进行并行 story 执行。如果此工具不可用，Phase 4 无法并行运行 |
| BMAD 技能实际可用数量 | 高 | 启动检测会报告可用技能数，但首次实际调用才暴露运行时故障 |
| 子 agent 超时边界 | 中 | 30 分钟对于复杂 story 可能不足。实际 TDD 循环时间未知 |
| 回退输出 vs 原生 BMAD 输出质量 | 中 | 结构验证通过 ≠ 语义质量等价 |
| Git worktree 在目标环境是否可用 | 中 | 需要 `git worktree` 支持——CI 环境可能受限 |

### 2.2 设计债务——有意推迟的功能

| 问题 | 优先级 | 触发条件 | 方案 |
|------|--------|---------|------|
| 无错误预算 / 降级验收 | P2 | Lighthouse 89 分但项目可接受时 | `warning_thresholds` + 降级路径 |
| 心跳驱动的合并队列锁 | P2 | 遇到 `.lock` 竞态条件时 | 30s 心跳 + 120s TTL |
| 每页面验收阈值 | P2 | 某些页面合法地无法达到全局阈值时 | story 文件中的 per-page 覆盖 |
| `--dry-run` / `--explain` 模式 | P2 | 用户反馈要求可预测性时 | 编排器决策审计日志 |
| 5 个冗余的 FSM 状态副本 | P2 | 需要修改状态定义时 | 提取到 `references/fsm-states.md` |
| 快速启动向导 | P1 | 新用户不知所措时 | 3 个问题 → 自动模式选择 + 跳过不必要的子阶段 |

### 2.3 结构性局限——当前架构无法解决的

| 局限 | 说明 | 可能的未来方向 |
|------|------|--------------|
| 53K 行规范，零自动化验证 | 所有一致性检查依赖人工审查。版本漂移、ID 冲突、引用断裂在静态分析中可检测但未自动化 | Pre-commit hook：验证版本一致性、ID 唯一性、变量引用完整性 |
| 子 agent 不能互相感知 | 设计特性而非缺陷——但意味着 story agent 无法协调共享逻辑的提取 | 故事间协调在合并后的 code review 阶段处理 |
| LLM 状态追踪的上限 | 40+ FSM 状态在 200K token 窗口内可追踪，但在 1M token 会话中可能漂移 | 编排器周期性 `rebuild-status` 自检：读取实际 status/ 文件并验证 FSM 一致性 |

## 三、过程洞察——从 5 轮审查中获得的经验

### 3.1 有效的做法

1. **多专家角色扮演审查。** 架构师发现了结构性矛盾。安全审计员发现了注入风险。UX 倡导者发现了可用性断层。没有单一视角能覆盖所有这些问题。

2. **Pre-mortem 分析。** "想象 6 个月后项目失败"这个练习在每一轮中都揭示了真实的风险，而直接的规格审查未能捕捉到这些风险——合并部分状态、隐性文件共享、BMAD 单点故障。

3. **增量修复并验证。** 每轮以扫描开始，以验证结束。版本漂移被反复检查，直到完全消除。

4. **"推迟，除非有数据"原则。** 41 项发现中的 11 项被确认为技术债务并有意推迟。这避免了过度工程化。

### 3.2 无效的做法

1. **手动批量编辑跨 25+ 文件。** `sed` 可以工作，但很脆弱。自动化验证脚本（检查版本一致性）应该在第 1 轮就写出来，而不是在第 5 轮。

2. **业务逻辑中使用 YAML 作为配置格式。** `customize.toml` 是 700+ 行。对于简单的键值对来说 TOML 很好，但嵌套的 `[bmad_skill_fallbacks]` 有 20 个条目，每个都有 `description`、`prompt_key` 和 `inputs`——这是结构化数据伪装成配置。一个专用的 `fallbacks.yaml` 会更清晰。

3. **基于上下文的变量约定，而非显式的写入目标。** "编排器根据上下文重定向 `{sprint_tracking}` 写入"的做法是务实的，但引入了隐性行为。未来的工作流应该使用显式的写入目标变量。

## 四、优化路线图

### 现在就可以做的（0 依赖）

```
□ Pre-commit 验证脚本
  - 版本一致性检查 (version: X.Y.Z 在所有文件中)
  - SRG/CA/MG ID 唯一性检查
  - 禁止模式检查 (不再有 "Pure Orchestrator")
  - sprint_tracking 写入引用检查
  
□ 快速启动向导
  - init 流程中添加 3 个复杂度问题
  - 自动选择模式 + 推荐子阶段跳过
  - 显示将运行什么 → 一次确认 → 执行
```

### 试点后做的（需要真实使用数据）

```
□ 基于复杂度的验收阈值
  - simple: 跳过 E2E BROWSER
  - standard: 当前默认值
  - complex: 当前 + 安全审计 + 负载测试

□ 回退输出质量基准
  - 运行 3 个 BMAD 原生项目
  - 运行 3 个纯回退项目
  - 比较 Phase 1-3 工件质量（人工评估）
```

### 不做的事情（架构上不合理）

```
✗ 子 agent 间协调 —— 违反 One-Story-One-Agent 原则
✗ 编排器加载工件正文 —— 破坏薄编排器边界
✗ 实时仪表盘 —— 超出 CLI 技能范围（需要 WebSocket/UI）
```
