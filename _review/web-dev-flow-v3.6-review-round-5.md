# 1. Pre-mortem 分析 — 剩余故障场景

## 故障链（极低概率）：Gate Card 版本不匹配导致门禁评估漂移

**场景：** Gate card 文件（`references/gate-cards/`）声明版本为 3.2.0。编排器读取 G3-05（用户确认）并应用 V3.4 的 auto_mode 降级规则。但如果门禁卡片中增加了新的检查类型，版本号差异可能导致编排器错误地假设某个功能不可用。

**缓解措施：** Gate card 版本是一个标签——门禁卡片本身的内容才是决定性的。编排器不检查门禁卡片的版本，只读取其中的内容。风险仅限于人类维护者：如果有人在未更新版本标签的情况下编辑了门禁卡片，版本号将产生误导。

## 故障链（极低概率）：Schema 版本落后导致验证漂移

**场景：** `sprint-status-schema.yaml` 声明版本为 3.6.0（正确），但 `artifact-frontmatter-schema.yaml` 仍为 3.0.0。第三方工具读取 schema 版本号可能错误地假设旧功能。

**缓解措施：** Schema 版本目前仅用于文档目的——没有自动化 schema 验证。一旦添加了自动化验证，schema 版本将成为功能性的。

## 当前设计是否符合目标？

**目标：** "24 小时端到端自动化 Web 项目开发"

- **Phase 1-3（规划+架构）：** 在自动运行模式下，8-14 个子阶段通过 BMAD/回退子 agent 自动化。人工审查点位于 Phase 门禁处。**可行。**
- **Phase 4 BE（实施）：** 每故事 TDD 循环 + CODE ACCEPTANCE + 原子合并。**可行。**
- **Phase 4 FE（实施）：** 每故事实施 + 4 层验收。浏览器验收需要真实浏览器基础设施。**有条件可行** — E2E 浏览器验收需要 CI 中的 Playwright/Cypress。
- **集成 + 回顾：** 合并队列处理 + 跨 Phase 审计。**可行。**

# 5. 代码审查挑战 — 最终评审

## 审查员 1：务实的架构师

*关注点：它能在真实项目中存活下来吗？*

**裁决：已准备好试点。**

系统现在可以作为一个整体进行推理。在过去 4 轮中：

- 版本碎片化（最令人担忧的信号）已完全解决
- 编排器模型已经从自相矛盾转变为原则性的澄清
- 每个 BMAD 技能依赖都有已配置的回退
- 合并队列现在可以处理隐含依赖和部分故障
- 自动运行暂停恢复为操作员提供情境感知

需要在下一次重大现实世界测试中关注三件事：
1. **子 agent 超时：** 30 分钟对于大型故事来说是否足够？第一个试点项目应该记录实际的故事实施时间。
2. **回退质量：** 内联子 agent 为缺失的 BMAD 技能产生的输出是否与原生技能质量匹配？前几个项目应该使用原生 BMAD 技能运行；回退应该故意测试。
3. **上下文边界：** ~38KB 的干净上下文设计在原理上是好的。但一个复杂的 500 行故事文件 + 500 行 api-spec + 200 行架构 = 可能 ~15KB——远在预算之内。

## 审查员 2：安全与可靠性审计员

*关注点：还剩下什么漏洞？*

**裁决：风险态势从第 1 轮降低了 ~90%。**

第 1 轮标记了 5 个关键安全问题：scope_write 路径遍历、命令注入、合并部分状态、隐性文件重叠和 BMAD 技能单点故障。全部 5 个问题在后续各轮中通过各种机制得到了缓解（SRG-04、SRG-09、原子合并、隐性检测、回退）。

残余风险：
- `npx --no-install` 是好的，但 `npx --no` 应该经过审查——它仍然运行本地二进制文件，但阻止了安装（这是期望的行为）
- 命令安全 allowlist 中的 17 个安全前缀可能需要审计项目特定的二进制文件
- 无沙箱——子 agent 对文件系统和网络具有完全访问权限（Claude Code Agent 固有的设计限制）

**最终建议：** 为 `forbidden_patterns` 添加 `"chmod "` 和 `"chown "`，在下一轮中完善安全态势。

## 审查员 3：UX 与开发者体验倡导者

*关注点：设计精湛程度是否与架构质量相匹配？*

**裁决：恢复仪表盘和错误翻译弥补了最大的 UX 差距。Phase 菜单仍然是原始的。**

自第 1 轮以来，我的三大批评已经得到解决：
1. ~~"错误消息是面向内部的"~~ → 16 个检查 ID 的人类可读翻译（R4）
2. ~~"自动运行暂停没有仪表盘"~~ → 恢复仪表盘显示合并状态 + 故事（R2）
3. "Phase 菜单需要建议的下一个操作" → 未解决，但自动运行模式使其变得不那么重要

5 轮后我最大的遗憾是：**学习曲线。** 201 个文件 / 53K 行是一个庞大的系统。一个新的开发者在没有导师的情况下采用这个工作流，在面对 "web-dev-flow init → 36 个子阶段 → 发生了什么？" 时，将会难以承受。

快速启动向导（R3-M4）是我积压工作中缺失的一项。它可以通过一个基于复杂度的分类函数修复"我不知所措"的前 5 分钟体验。在那之前，工作流假定用户已经阅读并理解了 53K 行规格——这是一个沉重的负担。
