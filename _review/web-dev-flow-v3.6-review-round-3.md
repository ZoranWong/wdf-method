# 1. Pre-mortem 分析 — 剩余故障场景

## 故障链 A（低概率）：SRG-08 冲突导致 Story Agent 混淆

**场景：** Phase 4 自动运行处理一个 story 时，该 story 的 `scope_write` 触及了受保护路径。编排器在分派前评估 Story Ready Gate。受保护路径检查（SRG-08a，第 106 行）标记该 story 为 `serial_only`。新的命令安全检查（SRG-08b，第 785 行）也使用相同的 ID。检测到哪个 SRG-08？如果检查执行顺序产生冲突结果（一个通过，一个失败），编排器可能错误地分派或阻止该 story。

**影响：** `serial_only` story 被错误地并行分派（覆盖了受保护路径）或安全 story 因受保护路径检查失败而被错误地阻止。

**缓解措施：** 立即解决 SRG-08 冲突 — 见第 4 节发现 R3-N1。

## 故障链 B（低概率）：拆分文件重建竞态条件

**场景：** 自动运行期间，BE 编排器写入 `status/phase-04-be.yaml`，同时主编排器开始重建 `sprint-status.yaml`（响应 `rebuild-status` 命令或定期刷新）。`cat status/phase-04-be.yaml` 读取到部分写入的内容。派生索引中存在瞬间不一致的状态。

**影响：** 显示的进度与实际的 story 状态瞬间不匹配。下次重建可自行纠正。

**缓解措施：** 重建操作暂停自动运行进度 1 秒，以确保文件 IO 刷新。或者，重建仅在空闲时运行（无活跃的自动运行进度）。

# 3. 第一性原理分析 — 边界测试

## 原则 1："薄编排器边界是否成立？"

**测试：** 是否有任何地方是编排器**必须**加载工件正文才能做出正确决策的？

**场景 1 — 门卡评估：** 编排器检查 `artifact_metadata`。工件前置元包含 `status`、`checksum`、`bmad_review_passed`。编排器验证前置元但不验证正文是否与前置元一致。**结论：** 成立。工件可以有一个 `status: approved` 的前置元和一个"lorem ipsum"正文——编排器不会检测到。这是设计上的取舍：信任子 agent，通过对不一致的校验和/内容进行定期采样审计。

**场景 2 — 跨 Phase 一致性：** 这是唯一需要跨越边界的地方，并且正确地委托给了 Phase 3.9 的专用子 agent。编排器不需要加载工件正文——它分派一个子 agent 来加载。**结论：** 成立。

**场景 3 — 自动运行暂停诊断：** 当故事失败时，编排器需要显示**出了什么问题**。恢复仪表盘从 status/ 文件和检查点提交消息中读取——而不是工件正文。它显示的是故事状态和检查点摘要，而不是代码差异。**结论：** 成立。

## 原则 2："36 个子阶段是否仍然成立？"

**当前状态：** 36 个子阶段 + 5 个全栈子工作流。推荐路径将最低要求减少到约 8 个 Phase 2 子阶段 + 8 个 Phase 3 子阶段 + 6-14 个 Phase 4 子阶段 = 最少 22 个子阶段。

**挑战：** "最低可行路径"是**文档化的**但从未被**强制执行**。用户仍然需要手动跳过每个可跳过的子阶段。这相当于在为 2 人团队运行的 CRUD 应用中，有 14 次"你想跳过这个吗？"的提示。

**建议：** 添加一个快速启动模式，该模式：
1. 一次性评估项目复杂度（简单 / 标准 / 复杂）
2. 自动跳过标记为高于当前层级的所有子阶段
3. 展示将运行什么并请求一次确认
4. 继续执行

## 原则 3："4 层验收是否对所有项目都有意义？"

**当前状态：** BE story 在 CODE_ACCEPTANCE 处停止。FE story 通过全部 4 层。这是硬编码的。

**挑战：** 对于一个内部管理仪表盘（5 个用户，仅限 Chrome），运行 E2E_BROWSER_ACCEPTANCE（Chrome + Firefox + Safari + 响应式 + 慢速 3G）是浪费的。对于一个关键任务支付系统，UI_ACCEPTANCE 层应该比内部维基更严格。

**建议：** 基于 `customize.toml` 中的 `complexity_tier` 添加层级配置：
- `simple`：CODE_ACCEPTANCE，FEATURE_ACCEPTANCE，UI_ACCEPTANCE（仅 Lighthouse），跳过 E2E 浏览器
- `standard`：全部 4 层（当前默认）
- `complex`：全部 4 层 + 额外的安全审计 + 负载测试

# 4. 批评与完善 — 第 3 轮发现

## 4.1 新发现

### 发现 R3-N1：SRG-08 ID 冲突（中等）

**位置：** `phase-04-implementation.md` 第 106 行 vs 第 785 行

两个不同的检查使用相同的 ID：
- **SRG-08（受保护路径，第 106 行）：** `scope_write` 与受保护路径的交集 → 标记为 `serial_only`
- **SRG-08（命令安全，第 785 行）：** `acceptance_check` 命令通过安全验证

这是不同的检查，应用于不同的上下文。如果编排器按 ID 跟踪检查结果，当两个 SRG-08 检查产生不同的结果时，一个会覆盖另一个。

**修复：** 将 Story Ready Gate 中的命令安全检查重命名为 SRG-09，释放 SRG-08 给受保护路径（该 ID 更早定义），或采用命名约定，如 `SRG-08-protected` 和 `SRG-08-command`。

### 发现 R3-N2：全栈模式集成债务（中等）

**位置：** `references/sub-workflows/fullstack/`（5 个文件）vs `SKILL.md` vs `phase-04-implementation.md`

全栈模式（Next.js/Nuxt/Remix/SvelteKit）拥有完整的 5 文件子工作流：
- `fs-1-scaffolding.md` — 项目初始化
- `fs-2-foundation.md` — ORM、认证、中间件
- `fs-3-stories.md` — 自动继续全栈故事实施
- `fs-4-qa.md` — 3 个验收门（特性 → UI → E2E 浏览器）
- `fs-5-review.md` — 最终审查 + 交付

然而：
- Phase 4 路由表将全栈模式列为"跳过 4.2-4.12，运行合并开发"
- 全栈故事实施（fs-3）缺少分离模式下存在的详细子步骤编号（4a、4b、4c...）
- 全栈模式未从第 2 轮改进中受益：无 SRG-04（路径安全）、无 SRG-08（命令安全）、无原子合并引用、无隐性依赖检测
- 全栈回顾（fs-5）未引用 V3.6 合并队列或隐性重叠检测

**修复：** 执行全栈子工作流上的第 2 轮改进的回溯移植，或明确将全栈模式文档化为"等同于分离规范中的 [链接到章节]"。

### 发现 R3-N3：BMAD 回退模板验证缺口（低）

**位置：** `customize.toml` `[bmad_skill_fallbacks]` 部分 — 20 个技能条目

回退配置引用提示键（例如，`prompt_key = "brainstorming_fallback"`），但实际的提示模板在 `references/prompt-templates/` 中。没有自动化机制来验证：
1. 提示模板存在于预期的文件路径中
2. 模板包含所有必需的 `{input_document}` 占位符
3. 模板的输出模式与原生 BMAD 技能匹配

**修复：** 在启动时添加回退模板验证：对于每个 `bmad_skill_fallbacks.{skill}.prompt_key`，验证 `references/prompt-templates/{prompt_key}.md` 存在且非空。

### 发现 R3-N4：恢复仪表盘数据源依赖（低）

**位置：** `SKILL.md` 自动运行暂停恢复仪表盘

仪表盘从多个来源读取：`status/phase-04-be.yaml`、`status/phase-04-fe.yaml`、`git branch`、`git worktree list`、`git log`、`status/merge-queue/items/`、`status/stories/`。如果其中任何一个来源临时不可用（例如，git 仓库损坏），仪表盘生成本身会因部分数据而失败。

**修复：** 对每个数据源使用防御性读取：如果 `git worktree list` 失败，显示"N/A"而不是使仪表盘崩溃。仪表盘必须始终渲染，即使某些来源不可用。

### 发现 R3-N5：受保护路径列表包含从未受保护的路径（低）

**位置：** `customize.toml` `protected_paths`

12 个受保护路径包括 `"shared/ui/shell"` 和 `"route/registry"`，这些是受保护路径通常不涵盖的特定应用程序路径。同时，`.env.production` 在 `forbidden_paths`（正确禁止）中，但 `.env.local` 和 `.env.development` 没有——它们是常见的密钥存储位置。

**修复：** 审查受保护路径与实际的现代 Web 应用程序结构。添加缺失的密钥路径通配符。

### 发现 R3-N6：故事切片 P0/P1 未与子步骤编号集成（低）

**位置：** `specs/story-slicing.md` vs `specs/step-audit.md`

故事切片定义了每个切片的 `scope_write` 和 `acceptance_check`，但子步骤编号（4a、4b、4c...）没有切片感知。如果一个故事有 P0 和 P1 切片，每个切片都需要自己的子步骤审计跟踪。当前设计假设每个故事有一个线性步骤序列。

**修复：** 添加基于切片的子步骤映射：`4c-P0`、`4d-P0` 等，或在切片头部文档中明确说明每个切片遵循相同的子步骤序列。

# 5. 代码审查挑战 — 三位风格化审查员

## 审查员 1："务实的架构师"

*关注点：它在生产中能生存下来吗？*

**裁决：已为试点项目准备就绪。在广泛采用之前需要全栈对等性和回退验证。**

两轮改进的系统令人印象深刻。原子合并协议（--no-commit → 检查 → 提交\|中止）是合并队列应如何运作的标准做法。SRG 门已正确排序（现在有 8 个门，从文件存在到命令安全）。薄编排器边界是原则性的。

三个值得关注的点：

1. **全栈模式是一种二等公民。** 5 个全栈子工作流文件存在于不同的演化阶段（V3.2 级别）。如果你正在构建一个 Next.js 应用——2026 年最流行的 Web 框架——你会得到一个低于分离模式的体验。为了使该工作流可信，必须进行对等。

2. **BMAD 回退未经测试。** 有 20 个回退提示键。它们对应的模板文件存在吗？在回退模式下它们产生什么工件？在试点之前，使用至少 3 个技能（理想情况下是创建 PRD、创建架构、创建故事）运行回退路径。

3. **52K 行规范对于"阅读整个文件"的 AI 编排器来说需要关注。** 编排器被告知要阅读门卡（~50 行）和提示模板（~100 行）。但子工作流文件是大型文档（4-4-be-api-endpoints.md 可能为 400+ 行）。编排器**不**读取这些——它只分派子 agent。然而，规范说编排器应该"如果内容较短，则读取整个文件"。52K 行的上下文会稀释注意力。相信薄编排器边界——不要加载子工作流文件。

**最后的话：** 如果在 3 个试点项目（小型 CRUD、中型 SaaS、大型全栈）上运行，并且回退路径经过测试，这个工作流将会成功。

## 审查员 2："安全与可靠性审计员"

*关注点：还剩下什么可以安全地被利用？*

**裁决：命令注入风险得到良好缓解。残留风险存在于外部依赖和重建竞争条件中。**

自第 1 轮以来，安全态势显著改善：

| 风险 | 第 1 轮 | 第 3 轮 |
|------|--------|--------|
| Story Agent 命令注入 | 🔴 关键 — 无消毒 | 🟢 低 — SRG-08 消毒 + 允许列表 |
| scope_write 路径遍历 | 🔴 关键 — 无验证 | 🟢 低 — SRG-04 路径安全 |
| 合并部分状态 | 🔴 关键 — 无中止 | 🟢 低 — 原子合并协议 |
| 隐性文件重叠 | 🔴 关键 — 无检测 | 🟡 中 — 已检测但未阻止 |
| BMAD 技能依赖 | 🔴 关键 — 单点故障 | 🟡 中 — 已回退但未测试 |

**新发现：** `acceptance_check_safety.allowed_prefixes`（第 2 轮新增）将 `"npx "` 列为允许。`npx` 可以从 npm 下载并执行任意包——它本质上与 `curl | sh` 相同。这应该是 `"npx --no-install "` 或限制为仅限项目本地的二进制文件。

**建议：** 收紧 `npx` 到 `"npx --no-install "`。添加 `allowed_prefixes_validation` 测试，验证每个允许的前缀不会无意中启用任意代码执行。

## 审查员 3："UX 与开发者体验倡导者"

*关注点：有人能在没有阅读 52K 行规范的情况下使用这个吗？*

**裁决：功能完整但学习曲线陡峭。推荐路径和仪表盘是好的起点。需要快速启动向导。**

自动运行暂停恢复仪表盘（第 2 轮新增）正是我所寻找的。它显示了合并状态、活跃工作、排队等待项和建议的下一步操作——全部集中在一个视图中。这是"出了什么问题以及我该如何修复"与"这里是内部的 SRG-05"的区别。

对于简单项目，仍然缺少一个**快速启动向导**。想象一个开发者输入 `web-dev-flow init`，描述他们的项目，然后被问到：

> "检测到复杂度：简单（<5 个 API 端点，<3 个页面，CRUD 模式）。"
> "推荐路径：跳过 Phase 1，最少 Phase 2 + 3，仅 BE 实施。"
> "预计时间：~2 小时（带人工审查）。"
> "[Y] 接受推荐  [C] 自定义"

这需要约 100 行代码——一个分类函数读取 customize.toml 中基于项目描述关键词的复杂度层级。它将使新用户的前 5 分钟从不知所措变为充满信心。
