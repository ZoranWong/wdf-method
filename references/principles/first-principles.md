# 第一性原理设计与问题分析准则

## 核心原则

**第一性原理（First Principles）**：将问题分解到最基本、不可再简化的真理层面，从零开始构建解决方案，而非通过类比推理。

> "I think it's important to reason from first principles rather than by analogy. The normal way we conduct our lives is we reason by analogy. We are doing this because it's like something else that was done. With first principles, you boil things down to the most fundamental truths and then reason up from there." — Elon Musk

---

## 第一性原理分析框架

### 阶段 0：问题锚定

在开始任何设计或分析之前，必须先回答：

```
1. 我们要解决什么问题？
   - 谁有这个问题？（具体的人，不是抽象的用户画像）
   - 他们现在怎么解决的？（现状是什么）
   - 为什么现有方案不够好？（量化的差距）

2. 解决这个问题值得吗？
   - 不解决会怎样？（不作为的代价）
   - 解决了会怎样？（成功的样子）
   - 谁来买单？（经济可持续性）

3. 为什么是我们/为什么是现在？
   - 什么变了使现在成为时机？（技术、监管、行为）
   - 为什么之前没人解决？（真实壁垒 vs 缺乏尝试）
```

### 阶段 1：假设解构

列出所有关于这个问题的假设，逐一挑战：

```
假设清单：
1. [假设] 用户需要 ______
   → 挑战：他们真的需要吗？证据是什么？
   → 替代：如果他们不需要 ______，实际需要的是什么？

2. [假设] 解决方案需要 ______
   → 挑战：为什么需要？有没有不需要的方式？
   → 替代：如果去掉 ______，系统还能工作吗？

3. [假设] 市场/行业标准是 ______
   → 挑战：这个标准的起源是什么？当时的约束还存在吗？
   → 替代：如果重新设计，考虑到今天的约束，最优解是什么？

4. [假设] 技术上必须使用 ______
   → 挑战：这个技术选择的假设条件是否仍然成立？
   → 替代：如果从零设计，考虑到实际约束，最简单的方案是什么？
```

### 阶段 2：根本原因分析

使用 **五个为什么（5 Whys）** 追溯到根本原因：

```
表面问题：用户流失率高

Why 1: 为什么用户流失？
→ 因为他们没有持续使用产品

Why 2: 为什么没有持续使用？
→ 因为产品没有解决他们的核心需求

Why 3: 为什么没有解决核心需求？
→ 因为我们假设的需求和实际需求不匹配

Why 4: 为什么不匹配？
→ 因为我们在做用户研究时没有区分"用户说的"和"用户做的"

Why 5: 为什么没有区分？
→ 因为我们依赖问卷调查而非行为观察

根本原因：需求发现方法论缺陷 — 依赖陈述性反馈而非行为数据
解决方案：改变需求发现方式，而不是改变产品功能
```

### 阶段 3：约束映射

识别所有约束，分类为真实约束 vs 假设约束：

```
真实约束（不可改变）：
- 物理定律：光速、热力学
- 数学真理：NP 完全性、CAP 定理
- 监管要求：GDPR、HIPAA（法律强制执行）

假设约束（可以挑战）：
- "行业惯例" — 只是惯例，不是真理
- "用户期望" — 用户可能期望是因为没见过更好的
- "技术限制" — 技术限制可能是历史遗留，今天已不适用
- "成本限制" — 可能可以重新分配或创新降低成本
- "时间限制" — 可能需要重新评估优先级
```

## 第一性原理设计准则

### 准则 1：从"Why"开始，而非"What"

```
❌ 类比推理：Uber for X / Airbnb for Y / Stripe for Z
✅ 第一性原理：
   - 用户需要的是什么？（信任、速度、便利？）
   - 经济上可行的最小单元是什么？
   - 技术上的最简实现是什么？
```

### 准则 2：最小可行约束

每增加一个约束，问自己：

```
- 这个约束是真实的还是假设的？
- 如果去掉这个约束，系统会怎样？
- 有没有更低成本的方式满足同样的约束？
```

### 准则 3：解耦到不可再分的单元

```
复杂系统 → 分解为独立的功能单元 → 每个单元可以独立理解、实现、验证

例如：支付系统
  不是"我们需要 Stripe"
  而是：
    1. 我们需要安全地传输支付信息
    2. 我们需要授权和捕获资金
    3. 我们需要对账和清算
    4. 我们需要处理退款和争议

  每个单元有独立的约束和实现选项
```

### 准则 4：从零开始重新发明

```
暂时忘记所有现有方案，问：
  "如果我从零开始，知道现在的所有信息，我会怎么设计这个系统？"

然后对比你的设计和现有方案：
  - 为什么现有方案做了不同选择？
  - 这些选择的理由今天还成立吗？
  - 哪些是历史包袱？哪些是深思熟虑的决策？
```

### 准则 5：可证伪性检验

每一个设计决策必须有可证伪的假设：

```
决策：使用微服务架构
可证伪假设："如果系统需要独立部署和扩展不同组件，微服务架构比单体架构更优"

验证方式：
  1. 列出真正需要独立扩展的组件（不是所有组件）
  2. 测量微服务带来的网络开销、运维复杂度
  3. 对比单体架构在相同场景下的性能和维护成本
  4. 如果独立扩展需求 < 3 个组件 → 微服务可能是过度设计
```

## 问题分析准则

### 准则 A：问题 vs 解决方案混淆

最常见的设计错误是混淆问题和解决方案：

```
用户说："我需要一个更好的仪表盘"
  → 问题（真正需要的）：更快地了解业务状态并做出决策
  → 解决方案（用户提出的）：更好的仪表盘
  → 可能的更好解决方案：自动预警、AI 摘要、推送通知、语音报告

核心问题：信息获取和决策效率
解决方案空间远大于"更好的仪表盘"
```

### 准则 B：症状 vs 根因

```
症状：用户在支付页面放弃率高
可能的根因：
  1. 支付页面加载慢（性能问题）
  2. 不支持用户偏好的支付方式（功能缺失）
  3. 总价与预期不符（心理问题 — 隐藏费用）
  4. 支付流程步骤太多（UX 问题）
  5. 用户只是想比价，不是真的想买（意图问题）

每个根因对应完全不同的解决方案
修复症状（"优化支付页面"）而不找到根因 = 浪费资源
```

### 准则 C：约束优先级排序

并非所有约束同等重要。按优先级排列：

```
P0（硬约束 — 违反则系统不可行）：
  - 法规合规（不满足不能运营）
  - 安全底线（数据泄露不可接受）
  - 核心功能正确性（不正确的系统没有价值）

P1（强约束 — 违反则系统质量严重下降）：
  - 性能基线（响应时间 <X ms 是可用性要求）
  - 可靠性基线（可用性 >= 99.X% 是业务要求）
  - 用户体验基线（核心流程完成率必须 >Y%）

P2（软约束 — 有最好，可以权衡）：
  - 技术栈偏好
  - 架构风格偏好
  - 额外功能需求
  - 非关键性能优化

P3（伪约束 — 可以放弃）：
  - "我们一直这样做"
  - "竞争对手这样做"
  - "这是最佳实践"
  - "用户可能想要"
```

### 准则 D：复杂度合理性检验

每增加一个复杂度，必须回答：

```
增加的复杂度：{描述}
带来的价值：{量化的价值，不是模糊的"更好的XXX"}
没有这个复杂度的替代方案：{更简单的替代方案}
为什么替代方案不够好：{具体的差距，不是感觉}

如果 "带来的价值" 无法量化 → 这是伪需求
如果 "替代方案" 能满足 80% 的需求 → 考虑替代方案
如果 "为什么不够好" 是猜测 → 先验证再增加复杂度
```

## 在设计流程中的应用

### Party Mode 集成

在每一轮 Party 开始前，Facilitator 执行第一性原理检查：

```
── First Principles Check ──

Round {N}: {TITLE}

假设解构：本轮的 3 个关键假设
  1. {假设} → 挑战：{为什么可能是错的}
  2. {假设} → 挑战：{为什么可能是错的}
  3. {假设} → 挑战：{为什么可能是错的}

约束验证：
  ✓ 真实约束：{N} 个
  ⚠ 假设约束：{M} 个需要验证
  ✗ 伪约束：{K} 个已移除

上一轮的最高风险假设：
  {从上一轮带过来的待验证假设}
─────────────────────────────
```

### 架构决策集成

每个 ADR 必须包含第一性原理分析段落：

```
### ADR-{NNN}: {TITLE}

第一性原理分析：
- 这个决策解决的根本问题是什么？
- 为什么现有方案不够好？
- 最简可行方案是什么？
- 为什么选择了这个方案而不是更简单的方案？
```

### 问题分析集成

在发现问题时，自动应用 5 Whys：

```
问题：{现象}
  → Why 1: {直接原因}
  → Why 2: {系统原因}
  → Why 3: {流程原因}
  → Why 4: {管理原因}
  → Why 5: {根本原因}

根因：{最底层的系统性原因}
修复根因的方案：{解决根本原因，而非修复症状}
```
